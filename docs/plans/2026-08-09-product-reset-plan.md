# CodeReader 产品复位实施与验收计划

**状态：** Accepted — 产品复位决策已于 2026-08-09 批准

**日期：** 2026-08-09
**依据：** `docs/architecture/2026-08-09-product-reset-decision.md`

## 1. 目标

在保留 CodeReader 生产安全、兼容和发布基础的前提下，把产品重新收束为一条完整、可恢复、可验证的代码认知流程：

> 从项目全貌开始，沿推荐路径进入真实代码，在代码和解释之间稳定往返，记录自己的理解与问题，并在变化和重启之后继续掌握项目。

本计划不是一次性大改版。每个阶段都必须产生独立可验证的产品增量；后续阶段不得用来掩盖前一阶段未解决的语义或数据问题。

## 2. 范围控制

### 2.1 本轮必须完成

- 项目优先的起始页和导航层级；
- 精简顶栏，外围能力归入设置、任务中心或更多菜单；
- 统一阅读节点、文件和路径的状态与进度口径；
- 项目地图、推荐路径和分层解释的连续导航；
- 用户笔记、问题、风险与通俗/详细解释模式；
- 相关代码跳转、解释陈旧与变化影响；
- 重启恢复、旧版本兼容、响应式和无障碍闭环；
- 公共定位、帮助、升级、故障排查和发布材料同步。

### 2.2 本轮不做

- 更名和全量品牌重做；
- 新文件类型、新模型供应商或模型市场；
- 通用聊天、代码编辑、代码生成或智能体执行；
- 云同步、账号体系和多人协作；
- 为追求指标而自动把模型输出标记为“用户已理解”。

## 4. 实施原则

1. **先统一语义，再调整视觉。** “已读、已解释、已理解、需复查”未定义清楚前，不新增进度组件。
2. **先做贯通路径，再做局部丰富。** 每一阶段都从打开项目验证到重启恢复，不以孤立组件完成代替用户流程完成。
3. **用户状态高于模型状态。** 模型生成了解释不等于用户理解了代码。
4. **兼容迁移优于重置数据。** 旧数据无法精确映射时，保留原值、标明来源并允许重新确认。
5. **外围能力退居后台但不降低质量。** 隐私、取消、恢复、诊断和发布证据继续执行现有生产门槛。
6. **所有异步结果绑定项目、文档、目标和版本。** 选择变化后，旧结果只能进入缓存或历史，不得覆盖当前界面。

## 5. 阶段计划

### R0：冻结、基线与决策批准

**目的：** 先建立共同完成定义，避免在实现中再次扩张。

**工作：**

- 批准产品复位决策，记录任何保留意见；
- 暂停非安全、非兼容、非发布阻断的新格式和供应商工作；
- 为当前起始页、项目打开、路径阅读、状态更新、重启恢复、窄窗口和错误恢复建立行为基线；
- 记录 `0.10.x`、`0.11.x` 数据样本以及当前数据库、提示词、模型配置和凭据引用格式；
- 给现有一级入口标注“核心、支撑、兼容、冻结”四类；
- 建立复位问题清单，明确负责人、依赖和验收证据位置。

**退出条件：**

- 架构决策获得维护者批准；
- 当前关键流程有可重复的测试或人工脚本，不依赖记忆比较；
- 兼容样本经过脱敏并能在隔离测试环境恢复；
- 没有未归类的一级入口或并行扩张项目。

### R1：统一掌握度和状态模型

**目的：** 消除顶栏、阅读路径、文件树和解释面板之间互相矛盾的进度。

**工作：**

- 定义 `visitState`（`unread | read`）、`masteryState`（`unconfirmed | understood`）和 `reviewState`（`current | needs_review`）；问题、风险和笔记为独立用户标注；
- 定义节点、文件、模块、路径和项目各自的聚合规则；
- 将“关键阅读路径掌握度”设为唯一一级百分比，分子为用户明确标记为已理解的路径节点，分母为路径节点总数；
- 所有局部百分比标注作用域、分子与分母语义；
- 为旧版 `ReadingState`、旧 IPC 和 `0.10.x`/`0.11.x` 进度建立确定性兼容映射、重算策略和回退路径，旧字段保留；
- 文档化文件访问、解释生成、用户确认和代码变化分别允许改变哪些状态；模型生成解释不得改变掌握度；
- 加入跨界面一致性测试、边界测试、属性测试、备份、事务、完整性检查和中断恢复测试。

**退出条件：**

- 同一状态在顶栏、路径、文件树和解释面板中完全一致；
- 路径节点、文件和项目统计不存在未解释的分母差异；
- 模型任务完成不会自动增加“已理解”；
- `0.10.x`、`0.11.x` 样本迁移后原始信息可追溯，失败可非破坏恢复；
- 迁移经过备份、事务、完整性检查和中断恢复测试。

**主要触点：** `src/features/project-guide/`、`src/features/reading-state/`、`src/app/hooks/useProjectProgress.ts` 以及对应 Rust 持久化层。实际模型以代码盘点为准。

### R2：恢复项目优先的信息架构

**目的：** 用户打开应用后，注意力立即落在“继续或开始理解一个项目”。

**工作：**

- 起始页以最近项目、继续阅读、打开项目和示例项目为主；
- 顶栏仅保留打开项目、继续阅读、模型健康、任务状态和更多菜单；
- 把模型详细配置、提示词注册表、反馈包、更新与发布信息迁到合理的二级位置；
- 让三栏分别稳定承担下一步、真实代码和解释意义；
- 为窄窗口设计显式的“路径 / 代码 / 解释”切换，不让解释落到不可见的页面尾部；
- 完成键盘路径、焦点管理、语义标签、缩放和高对比度检查。

**验收场景：**

1. 首次用户无需打开设置即可进入示例项目并获得第一条解释；
2. 老用户启动后一次操作即可继续上次项目和位置；
3. 在最小支持窗口中，用户可用键盘从路径节点到代码再到解释，并返回原节点；
4. 所有支撑能力仍可发现，但不会打断黄金路径。

**主要触点：** `src/app/App.tsx`、`src/app/styles.css`、项目打开与工作区布局相关组件。实际改动前以 R0 盘点为准。

### R3：补齐代码认知闭环

**目的：** 从“能看代码和解释”提升到“能逐层建立、保存和修正项目心智模型”。

**工作包：**

1. **项目与模块解释**：补齐项目、模块、文件、函数/代码块/行的上钻和下钻；
2. **相关代码导航**：解释中的依赖、调用、数据流和风险指向稳定目标，并可返回原位置；
3. **个人认知层**：支持笔记、问题和风险标记，明确区分用户内容与模型内容；
4. **解释深度**：暴露通俗/详细模式，并保持相同目标、版本和导航上下文；
5. **变化影响**：代码变化后标记受影响的解释和理解记录，提供复查队列；
6. **持久恢复**：重启后恢复项目、路径、当前位置、解释模式、个人记录和待复查项；
7. **失败处理**：模型不可用、响应取消、解释失败和项目移动时，代码阅读与已有记录仍可用。

**验收场景：**

- 用户从项目地图进入一个模块，再进入关键函数，读完后能原路返回并看到掌握度更新；
- 用户写下问题、切换解释深度、关闭应用后重新打开，所有上下文正确恢复；
- 修改已理解节点的代码后，对应解释和理解状态进入“需复查”，未受影响节点保持不变；
- 快速切换项目和文件时，迟到的模型响应不会覆盖当前目标；
- 相关代码跳转失败时提供原因和恢复动作，不丢失原选择。

**主要触点：** `src/features/explanation-panel/`、`src/features/project-guide/`、`src/features/reading-state/`、模型任务协调层与 Rust 数据模型。所有新增持久字段需先完成迁移设计评审。

### R4：公共定位和真实项目验证

**目的：** 证明复位后的产品不仅结构正确，而且真实有用，并让公开承诺与行为一致。

**工作：**

- 统一应用内文案、README、中文指南、安装/升级/卸载、故障排查、版本历史和发布说明；
- 用至少三类真实 AI 生成项目验证：小型脚本/工具、前端应用、含前后端或数据层的多模块项目；
- 每类项目覆盖首次进入、找到入口、理解一条关键路径、记录问题、重启恢复和代码变化复查；
- 记录失败点、用时、需要外部帮助的次数和用户能否复述项目结构；
- 检查空项目、大项目、非 UTF-8、符号链接、权限拒绝、项目移动和模型离线等边界；
- 更新已知限制，不把计划能力写成现有能力。

**研究目标：**

- 首条有意义解释在正常本地环境下不超过 1 分钟；
- 大多数目标用户在 5 分钟内能指出入口、核心模块和一条主要数据或控制路径；
- 解释与阅读位置重启恢复成功率不低于 95%；
- 关键阅读路径完成率达到或超过 60%；
- 代码变化场景中，应失效解释的识别率不低于 80%。

这些是产品验证目标，不是未经测量即可宣传的 SLA。样本、环境、失败和统计口径必须随结果保存。

### R5：发布候选与受控推出

**目的：** 将已验证的复位体验纳入 1.0 候选，而不是用本地绿灯替代发布证据。

**工作：**

- 从干净检出执行前端、Rust、迁移、隐私、竞态、无障碍、文档和打包门禁；
- 在 Windows/Linux 的 x64/ARM64 原生环境完成安装、启动、打开项目、解释、恢复、升级和卸载冒烟；
- 生成并核验校验和、SPDX SBOM 和制品证明；
- 只有 Authenticode 实际验证通过时才称 Windows 包已签名；
- 对数据库变更演练升级失败、回滚和备份恢复；
- 发布说明清楚区分新增、变化、兼容行为和已知限制；
- 先进入内部/候选通道，观察崩溃、迁移失败、陈旧覆盖和恢复失败，再决定公开发布。

**退出条件：**

- 完整平台矩阵和原生冒烟均有可审计证据；
- 旧版本兼容、诊断脱敏和目标绑定竞态门禁通过；
- 没有阻断黄金路径的 P0/P1 问题；
- 公共文档与实际制品逐项一致；
- 维护者明确批准公开发布。

## 6. 横向验证矩阵

每个阶段合入前，根据影响范围执行以下门禁；R5 必须执行完整集合：

| 维度         | 最低证据                                                         |
| ------------ | ---------------------------------------------------------------- |
| 前端行为     | 单元、集成、关键用户流程和错误状态测试                           |
| 视觉与响应式 | 支持窗口范围截图或自动化对比，含缩放与长文本                     |
| 无障碍       | 键盘全流程、焦点、名称/角色/状态、对比度与缩放                   |
| Rust/IPC     | 单元、集成、错误映射、权限边界和取消测试                         |
| 持久化/迁移  | 备份、事务、完整性、中断恢复、旧版样本升级                       |
| 隐私         | 诊断导出与日志扫描，确认无源码、提示词、响应、凭据和个人绝对路径 |
| 竞态         | 快速切换项目/文件/目标、取消、迟到响应和重启恢复                 |
| 性能         | 大项目索引、首次解释、切换、恢复和内存基线                       |
| 包与平台     | Windows/Linux x64/ARM64 原生安装和核心流程冒烟                   |
| 文档         | 定位、安装、验证、升级、卸载、排障、发布说明和限制一致性         |

单项绿灯只证明该门禁通过，不代表产品复位或公开发布完成。

## 7. 数据与回退策略

- 所有数据库模式变化先创建并验证仓库外备份，再在事务中迁移并运行完整性检查；
- 旧字段优先保留，新的掌握度从可追溯原始状态派生，禁止直接覆盖无法逆推的数据；
- UI 信息架构变化应允许在候选阶段通过受控开关回到旧导航，但两套界面不得长期分叉业务语义；
- 新的笔记、问题、解释模式和陈旧记录必须有向后兼容或明确的降级读取行为；
- 回退演练需要覆盖应用版本回退、迁移失败、项目路径变化和模型配置不可用；
- 发现数据损坏、隐私泄露或陈旧任务覆盖时，停止推出并保留证据，不以静默重置用户数据恢复。

## 8. 风险与控制

| 风险                         | 控制                                                 |
| ---------------------------- | ---------------------------------------------------- |
| 精简入口导致老用户找不到功能 | 保留二级入口、首次迁移提示和文档索引，并测试可发现性 |
| 新进度模型破坏旧记录         | 使用兼容映射、可重算派生值、备份和回退演练           |
| 项目地图或解释给出虚假确定性 | 显示来源、范围、版本、未知项和陈旧状态，允许用户修正 |
| 多层解释扩大模型成本和等待   | 缓存目标绑定结果，按需生成，明确任务状态与取消       |
| 窄窗口为适配而丢失关系       | 使用上下文保持的面板切换，并纳入键盘与最小窗口验收   |
| 复位再次演变成视觉改版       | 以端到端场景、状态一致性和用户认知结果作为退出条件   |
| 为赶 1.0 跳过平台证据        | 将完整平台矩阵保留为独立发布硬门禁                   |

## 9. 复位完成定义

只有同时满足以下条件，才可以宣布“产品复位完成”：

1. 产品复位架构决策已经批准；
2. R1–R4 的端到端验收场景全部通过；
3. 关键阅读路径掌握度在所有界面语义一致；
4. 项目、模块、文件和局部代码解释可以连续上钻、下钻；
5. 笔记、问题、风险、解释模式和待复查状态可持久恢复；
6. 变化影响和目标绑定竞态门禁通过；
7. `0.10.x`、`0.11.x` 兼容样本通过升级和非破坏恢复；
8. 真实项目验证达到预定目标，未达项有明确决策而非被隐藏；
9. 所有公共文档与实际产品定位、行为和限制一致；
10. 从干净检出获得相关前端、Rust、迁移、隐私、竞态、无障碍和文档门禁证据。

“复位完成”仍不等于“1.0 可公开发布”。公开发布还必须单独满足 R5 的完整原生平台、制品、SBOM、证明和维护者批准要求。

## 10. 第一批可执行任务

架构决策批准后，按以下顺序启动，不并行改动核心语义：

1. 建立 R0 行为基线和旧版兼容样本；
2. 先为理解状态和进度聚合写正式数据语义说明、兼容映射、迁移/回退设计与测试表；
3. 在状态模型及兼容迁移评审通过后统一进度模型；
4. 再画出现有与目标入口树，确认所有外围能力的新位置；
5. 随后实现起始页和顶栏的信息架构，再实现窄窗口面板切换；
6. 依次补齐个人认知层、分层解释、相关跳转和变化影响；
7. 每完成一个闭环即在真实项目上验证，不把所有验证推迟到发布前。

每一项实施任务都应包含：用户场景、数据影响、隐私影响、竞态风险、无障碍要求、回退方式、自动化测试和需要的原生验证。未经这些字段评审，不进入实现。
